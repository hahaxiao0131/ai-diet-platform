# 测试与验收标准

**适用版本：V1.1 / P0.1**

## 1. 验收原则

P0成功的标准不是页面完成，而是以下链路可以稳定跑通：

```text
登录
→ 建档
→ 目标确认
→ 记录一餐
→ 用户确认
→ 营养计算
→ 评分和风险
→ 今日更新
→ 下一餐What-if
→ 保存计划餐
→ 转正式记录
```

## 2. 环境验收

### A-ENV-001 本地启动

验收：

* PostgreSQL可以启动；
* FastAPI可以启动；
* 前端可以启动；
* 健康检查接口返回200；
* Mock Provider可以被业务层调用。

### A-ENV-002 数据库初始化

验收：

* 迁移可以从空数据库执行；
* 重复执行不会破坏数据；
* 基础食物和菜谱种子数据可以加载；
* 测试数据与正式数据隔离。

## 3. 账号和建档

### A-AUTH-001 新用户登录

验收：

* Mock登录返回独立user_id；
* 新用户标记为`is_new=true`；
* 不使用openid作为业务主键。

### A-PROFILE-001 完成建档

验收：

* 4步流程可完成；
* 必填字段校验正确；
* 体重支持0.1kg；
* 未完成建档不能进入目标确认；
* 建档完成后可以进入今日首页。

## 4. 目标管理

### A-GOAL-001 生成目标提案

验收：

* 后端根据档案计算目标；
* 返回能量、蛋白质、脂肪、碳水；
* 返回rule_version；
* 返回计算依据；
* 前端不自行计算目标。

### A-GOAL-002 修改目标需确认

验收：

* 修改关键档案后生成新旧目标对比；
* 用户未确认时旧目标继续生效；
* 确认后生成新的goal_version；
* 历史目标版本保留。

## 5. 饮食草稿

### A-DRAFT-001 Mock图片识别

验收：

* 上传1张图片可以创建草稿；
* 最多支持3张同餐图片；
* Mock返回结构化foods数组；
* 每项包含名称、份量、单位和可信度；
* 识别结果不会直接进入正式meal。

### A-DRAFT-002 修改识别结果

验收：

* 可以修改名称；
* 可以修改家用单位；
* 可以输入精确克数；
* 可以修改实际食用比例；
* 可以删除项目；
* 可以添加漏识别食物；
* 修改过程可恢复。

### A-DRAFT-003 确认草稿

验收：

* 未确认项目不能保存；
* 确认后创建正式meal；
* 确认后执行营养计算；
* 确认后执行评分；
* 确认后执行风险检查；
* 失败时整体事务回滚。

## 6. 营养计算

### A-NUTRITION-001 单项计算

验收：

* 基于每100g营养数据计算；
* 份量换算正确；
* 食用比例计算正确；
* 小数位符合约定；
* 保存nutrition_version；
* 不依赖大模型返回的营养值。

### A-NUTRITION-002 复合菜计算

验收：

* 标准菜谱可以展开组成；
* 用户可以修改组成；
* 修改后重新计算整道菜；
* 历史记录保存营养快照。

## 7. 评分和风险

### A-SCORE-001 单餐评分

验收：

* 返回总分和分项得分；
* 返回评分理由；
* 最多突出3个主要问题；
* 评分不受连续打卡影响；
* 评分不受AI使用次数影响。

### A-SCORE-002 数据不足

验收：

* 无记录时不生成最终评分；
* 数据不足时显示对应状态；
* 低可信度数据不会被包装成精确结论；
* 有部分记录时显示partial状态。

### A-RISK-001 硬性风险

验收：

* 命中过敏原时生成高优先级风险；
* 命中绝对禁用时阻止方案保存；
* 风险不只表现为扣分；
* 风险结果保存独立快照。

## 8. 今日首页

### A-TODAY-001 今日汇总

验收：

* 显示当前状态；
* 显示目标和已摄入；
* 显示剩余能量；
* 显示蛋白质等营养缺口；
* 显示接近上限的营养；
* 显示餐次卡片；
* 新增或修改餐后自动更新。

## 9. 下一餐和What-if

### A-PLAN-001 生成方案

验收：

* 返回2～3套方案；
* 方案营养接近当前缺口；
* 方案遵守硬性禁用；
* 方案显示推荐理由；
* 方案显示可信度或估算说明。

### A-PLAN-002 替换食材

验收：

* 返回替换选项；
* 替换后重新计算营养；
* 替换后重新执行RiskEngine；
* 替换后重新评估整餐；
* 不能只修改展示名称。

### A-PLAN-003 计划餐转正式记录

验收：

* 计划餐可以保存；
* 吃完后可以转正式记录；
* 可以修改实际份量和食用比例；
* 转换后计划状态变为converted；
* 重复转换被阻止。

## 10. 数据一致性

必须测试：

* 重复提交不会创建重复meal；
* 删除meal后当天数据正确重算；
* 修改历史meal后周围数据不被破坏；
* 目标版本变化不会修改历史快照；
* AI动作未确认时不写入业务数据；
* 业务模块不能绕过Provider。

## 11. 测试分层

```text
单元测试：规则、单位换算、评分、风险
集成测试：API、数据库、Provider
端到端测试：完整P0链路
人工验收：中文文案、交互、风险提示
```

## 12. 发布门槛

P0不得存在以下问题：

* 营养计算与后端不一致；
* AI识别结果未经确认进入正式记录；
* 过敏风险只扣分不拦截；
* 修改餐记录后首页数据不更新；
* 计划餐替换后未重新计算；
* 历史评分随规则升级静默变化；
* 真实用户数据进入测试环境。
